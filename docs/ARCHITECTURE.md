# 아키텍처

## 무엇을 만들었나

치지직 스트리머가 자기 채널에 챗봇을 붙여 쓰는 **SaaS 플랫폼**입니다.
네 개의 영역으로 나뉩니다.

| 영역          | 위치                           | 하는 일                                    |
| ------------- | ------------------------------ | ------------------------------------------ |
| ① 사용자      | `apps/web` (공개 · 마이페이지) | 기능 소개, 요금제, 결제, 내 채널·구독 관리 |
| ② 관리자      | `apps/web` (`/dashboard`)      | 스트리머가 자기 채널의 봇을 설정           |
| ③ 내부 관리자 | `apps/backoffice`              | 사용자·채널·구독·환불·감사 로그            |
| ④ Core        | `apps/core`                    | 치지직 세션, `!입장` 게이트, 명령 실행     |

세 개의 프로세스가 돕니다.

```
 ┌──────────────┐        ┌──────────────┐
 │  apps/web    │        │apps/backoffice│      브라우저
 │  :5173       │        │  :5174        │
 └──────┬───────┘        └───────┬───────┘
        │  /api (쿠키 세션)      │
        └────────────┬───────────┘
                     ▼
              ┌─────────────┐        ┌──────────────┐
              │  apps/api   │ ─────▶ │  apps/core   │  내부 토큰 인증
              │   :4000     │◀────── │    :4100     │
              └──────┬──────┘        └──────┬───────┘
                     │                      │
                     ▼                      ▼
              ┌──────────────┐       ┌──────────────┐
              │  PostgreSQL  │       │  치지직 API  │
              └──────────────┘       └──────────────┘
```

### 왜 API 와 Core 를 나눴나

수명이 다르기 때문입니다. API 는 프런트 문구 하나 고쳐도 재배포하지만,
Core 를 재시작하면 **모든 방송의 채팅 세션이 끊깁니다**. 한 프로세스에 두면
사소한 배포가 방송 사고가 됩니다.

Core 가 죽어 있어도 API 는 살아 있어야 합니다 — 설정 저장과 결제는 계속
되어야 하니까요. 그래서 `CoreClient` 의 실패는 전부 502 로 감싸고, "봇이
응답하지 않는다" 로 보이게 합니다.

## 디렉터리

```
apps/
  api/          REST API 게이트웨이 (Fastify)
  core/         봇 런타임 워커
  web/          사용자 웹 + 채널 관리자 대시보드 (Vite/React)
  backoffice/   내부 관리자 콘솔 (Vite/React)

packages/
  contracts/        zod 스키마 · DTO — 서버와 프런트가 함께 씁니다
  database/         Prisma 스키마 + 리포지토리 (테넌트 격리를 강제)
  bot-engine/       채팅 한 줄을 해석하는 순수 도메인 (저장소를 모릅니다)
  chzzk-sdk/        치지직 Open API 클라이언트 (우리 도메인을 모릅니다)
  auth/             치지직 OAuth · 세션 · 토큰 암호화 · RBAC
  billing/          요금제 · 구독 수명주기 · PortOne 어댑터
  ui/               두 프런트가 공유하는 디자인 시스템
  logger/           로깅
  platform-config/  환경 변수 스키마 · 서비스 상수

tooling/            tsconfig · eslint · prettier 공유 설정
infra/              docker-compose (로컬 Postgres)
docs/               이 문서와 봇 기능 레퍼런스
```

### 의존 방향

```
apps/*  ──▶  packages/{auth,billing,database,bot-engine}  ──▶  packages/{contracts,chzzk-sdk,logger,platform-config}
```

거꾸로 가는 화살표는 없습니다. 특히:

- **`chzzk-sdk` 는 우리 도메인을 모릅니다.** 테넌트도, 구독도, 봇 설정도 모릅니다.
  치지직 API 가 바뀌면 여기만 고칩니다.
- **`bot-engine` 은 저장소를 모릅니다.** 필요한 것은 전부 `ports.ts` 의 인터페이스로
  받습니다. 같은 엔진이 로컬에서는 JSON 파일로, 서비스에서는 Postgres 로 돕니다.
- **`database` 밖으로 Prisma 타입이 나가지 않습니다.** 리포지토리는 언제나
  `contracts` 의 모양으로 돌려줍니다.

### 내부 패키지 해석 방식

패키지들은 빌드 산출물이 아니라 **TypeScript 소스를 그대로** 내보냅니다
(`"exports": "./src/index.ts"`). 덕분에 패키지를 고칠 때 빌드를 먼저 돌릴
필요가 없고, 에디터에서 정의로 이동하면 실제 소스가 열립니다.

- 개발: `tsx`(Node) 와 Vite 가 TypeScript 를 직접 읽습니다.
- 배포: `tsup` 이 워크스페이스 패키지를 번들에 포함시킵니다(`noExternal`).

## 테넌시

**테넌트 = 채널 워크스페이스** 입니다. 치지직 채널 하나에 하나씩 생깁니다.

규칙은 세 가지이고 예외가 없습니다.

1. 사용자가 만든 모든 데이터에 `tenantId` 가 있습니다.
2. 조회는 언제나 `tenantId` 로 좁힙니다.
3. 테넌트를 지우면 딸린 데이터도 함께 지워집니다.

API 의 모든 채널 경로는 `/api/tenants/:tenantId/...` 이고,
`requireTenant()` 훅이 **매번 멤버십을 조회**해 권한을 확인합니다.
URL 의 tenantId 를 신뢰하지 않습니다 — 남의 채널 ID 를 주소창에 넣어 보는 건
가장 먼저 시도되는 공격이고, 여기가 유일한 방어선입니다.

내부 관리자에게도 자동으로 열어주지 않습니다. 고객 지원은 `/api/admin/*` 를
쓰게 해서, 남의 채널을 들여다본 기록이 감사 로그에 남게 합니다.

### 권한 두 축

| 축             | 값                                        | 뜻                        |
| -------------- | ----------------------------------------- | ------------------------- |
| `platformRole` | MEMBER · SUPPORT · OPERATOR · SUPER_ADMIN | 우리 서비스 안에서의 지위 |
| `tenantRole`   | VIEWER · MANAGER · OWNER                  | 그 채널 안에서의 지위     |

둘을 합치면 "내부 관리자면서 자기 채널에서는 스트리머" 를 표현할 수 없습니다.
실제로 우리 팀원도 자기 채널을 운영합니다.

검사는 `packages/auth/src/rbac.ts` 의 `staffCan.*` / `tenantCan.*` 로만 합니다.
라우트에서 역할을 직접 비교하면, 역할을 하나 추가할 때 반드시 어딘가를 빠뜨립니다.

## `!입장` 흐름

요구사항의 핵심입니다. 봇은 **연결돼 있어도 부르기 전에는 말하지 않습니다.**

```
1. Core 가 구독이 살아 있는 채널을 DB 에서 읽는다        (BotSupervisor.reconcile)
2. 채널마다 치지직 세션을 연다                            → 상태 IDLE
3. 스트리머·매니저가 채팅에 !입장                         (BotRuntime.handleJoinGate)
4. 상태 JOINED · 주기 메시지 시작 · 명령어 응답 시작
5. !퇴장 또는 대시보드 버튼 → 다시 IDLE
```

설계상 정해 둔 것들:

- **입장 명령은 금칙어 검사보다 먼저** 봅니다. 봇을 부르는 말이 금칙어에 걸려
  영영 못 부르는 상황을 막기 위해서입니다.
- **채팅 매니저도 입장시킬 수 있습니다.** `isAdmin`(=`manageCommands` 설정)이
  아니라 `canControlBot` 을 씁니다 — 명령어를 만드는 권한과 봇을 부르는 권한은
  성격이 다르고, 방송 중에 못 부르면 그건 설정이 아니라 결함입니다.
- **채팅과 버튼이 같은 경로**(`BotRuntime.setJoined`)를 씁니다.

### 조정(reconcile) 방식

Core 는 이벤트에 반응하지 않고, "바라는 상태" 와 "지금 상태" 를 1분마다
비교해 차이만 메웁니다. 이벤트 방식이면 신호를 한 번 놓친 채널이 다음
재시작까지 돌아오지 않습니다.

워커가 SIGKILL 로 죽으면 DB 의 상태는 JOINED 인 채 굳습니다. 그래서 상태를
**읽는 쪽**에서 하트비트를 함께 보고 판정하고(`toInstanceState`), 새 워커는
부팅 직후 `reapStale()` 로 죽은 워커의 자리를 치웁니다.

## 명령 실행 API

`POST /api/tenants/:id/commands/execute`

채팅을 거치지 않고 명령을 실행해 결과 문자열을 바로 받습니다.
대시보드 미리보기와 외부 연동(오버레이·디스코드)이 같은 경로를 씁니다.

핵심은 **채팅과 같은 엔진을 탄다**는 것입니다. `BotRuntime.resolveCommand` 하나를
채팅 파이프라인과 API 가 공유하므로, 미리보기에서 본 문장이 실제 응답과
달라질 수 없습니다.

기본값은 `broadcast: false` — 설정을 시험해 보는 행동이 방송에 새어 나가면
안 됩니다.

## 결제

- PG: **PortOne V2** (빌링키 기반 정기결제)
- 어댑터 인터페이스(`PaymentGateway`) 뒤에 두어, 테스트에서 실패·재시도·환불
  경로를 실제 결제 없이 검증합니다. `PORTONE_MOCK=true` 로 로컬에서도 전 흐름을
  눌러 볼 수 있습니다(프로덕션에서는 부팅 시점에 막힙니다).

카드 정보는 우리 서버를 지나가지 않습니다. 브라우저가 PG 창에서 직접 입력하고
**발급 식별자(issueId)** 만 넘기면, 서버가 그것으로 PG 에 다시 물어 빌링키를
받습니다. 클라이언트가 준 빌링키를 그대로 믿으면 남의 빌링키를 자기 계정에
붙일 수 있습니다.

### 상태 전이

```
 TRIALING ──(체험 종료·카드 있음)──▶ ACTIVE ──(결제 실패)──▶ PAST_DUE
     │                                 │                        │
     │(카드 없음)                       │(해지 신청)              │(3일 유예 후)
     ▼                                 ▼                        ▼
  EXPIRED  ◀──(기간 종료)──────────  CANCELED ───────────────▶ EXPIRED
```

전이는 `SubscriptionService` 한 곳에만 있습니다. 라우트나 배치가 직접
`status` 를 쓰지 않는 것이 규칙입니다 — 흩어지면 "왜 이 사람 봇이 멈췄는가" 에
아무도 답할 수 없게 됩니다.

- **업그레이드는 즉시**, 남은 기간만큼 차액만 청구합니다(일 단위, 원 단위 내림).
  방송 직전에 기능이 필요해 결제하는 경우가 대부분입니다.
- **다운그레이드는 기간 종료 후**. 이미 낸 만큼은 쓸 수 있어야 합니다.
- **결제 실패는 3일 유예 + 3회 재시도.** 카드 한도는 며칠이면 풀리는데, 그 사이
  방송에서 봇이 사라지면 사용자는 원인도 모른 채 이탈합니다.
- **만료돼도 데이터를 지우지 않습니다.** 무료 플랜으로 내려 한도만 좁힙니다.

웹훅은 서명(Standard Webhooks)으로 검증하고, `WebhookEvent.eventId` 유니크
제약으로 멱등 처리합니다. PG 웹훅은 재전송이 정상 동작이라 멱등성은 선택이
아닙니다.

## 보안에서 정해 둔 것들

| 항목                 | 결정                                                        |
| -------------------- | ----------------------------------------------------------- |
| 치지직 리프레시 토큰 | AES-256-GCM 으로 암호화해 저장 (`TOKEN_ENCRYPTION_KEY`)     |
| 로그인 세션          | DB 세션 + 해시 저장 (JWT 아님 — 즉시 무효화가 필요)         |
| 세션 쿠키            | httpOnly · sameSite=lax · 프로덕션 secure                   |
| OAuth CSRF           | state 를 쿠키에 심고 콜백에서 대조                          |
| API ↔ Core           | 공유 비밀 토큰, 상수 시간 비교, 기본 루프백 바인딩          |
| 내부 관리자 콘솔     | 권한 없으면 403 이 아니라 **404** (존재 자체를 알리지 않음) |
| 관리 동작            | 사유 필수 + 감사 로그(수정·삭제 불가)                       |
| 결제 웹훅            | 서명 검증 + 타임스탬프 5분 + 멱등 처리                      |
| 레이트 리밋          | 로그인 전 IP, 로그인 후 사용자 단위                         |

## 로컬 실행

```bash
pnpm install
pnpm infra:up          # Postgres
cp .env.example .env   # 값 채우기 (아래 참고)
pnpm db:migrate
pnpm db:seed           # 요금제 카탈로그 반영

pnpm dev               # 네 앱을 한꺼번에 (turbo)
# 또는 따로
pnpm dev:api           # :4000
pnpm dev:core          # :4100
pnpm dev:web           # :5173
pnpm dev:backoffice    # :5174
```

비밀 값 세 개는 직접 만들어야 합니다.

```bash
openssl rand -base64 32   # TOKEN_ENCRYPTION_KEY
openssl rand -hex 32      # SESSION_SECRET
openssl rand -hex 32      # INTERNAL_API_TOKEN
```

`BOOTSTRAP_SUPER_ADMIN_CHANNEL_ID` 에 자기 치지직 채널 ID 를 넣고 시드를 돌리면
그 계정이 최고 관리자가 되어 `:5174` 콘솔에 들어갈 수 있습니다.
